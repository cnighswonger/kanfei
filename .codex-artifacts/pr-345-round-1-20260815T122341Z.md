## What Is Correct

The handoff compile defects were corrected in the PR: `Theme.chart` is a single merged object, `createCustomTheme` no longer contains the pasted interface fragment, and the theme files do not have duplicate `chart` blocks or stranded `surface` strings.

The merged `chart` shape covers the two intended call sites without loss: `series.*` carries the future multi-series Highcharts ramp, while `trace`, `traceSecondary`, `traceShadow`, `traceFillOpacity`, `gridMinor`, `gridMajor`, `axis`, `grid`, `gridSoft`, and `surface` cover the current single-trace History/Trend chart needs. The PR leaves current shipped chart consumers unchanged, so these fields are inert until later wiring.

`deserializeCustomTheme` correctly backfills a pre-refactor custom theme that only has the legacy `colors`, `fonts`, `gauge`, and optional `fontScale` groups. It merges the new top-level groups from `themes[defaultTheme]`, preserves legacy custom overrides, and specifically deep-fills `chart.series` so missing ramp keys do not become `undefined`.

`defaultTheme` remains `dark`, and the dark/light theme legacy colors, font-family strings, gauge values, and `fontScale` match `origin/ui/refactor`.

## Blockers

1. `frontend/src/themes/classic.ts:34` changes the shipped Classic success color from `#4a7c3f` on `origin/ui/refactor` to `#3f6b35`. That is not invisible: `--color-success` is used throughout shipped screens for rising trends, connected indicators, calibration pass states, settings result messages, Spray go states, and other live UI. The PR comments claim Classic colors are unchanged, and the review request explicitly requires current dark/light/classic colors to match pre-refactor values. Restore `colors.success` to `#4a7c3f`. If `chart.series.humidity` intentionally wants the darker paper green, keep that separate from the legacy semantic success token.

## What Needs Attention

`frontend/src/context/ThemeContext.tsx:55-62` publishes type role variables with the raw object key in the CSS variable name. That makes `sectionLabel` become `--type-sectionLabel-family`, unlike the rest of this mapper, which kebab-cases camelCase names (`--color-bg-secondary`, `--dial-grad-outer`). Downstream CSS will naturally look for `--type-section-label-family`; either kebab-case `roleName` here or explicitly document that type role CSS names preserve TypeScript casing. I would fix it now because this PR is the token contract landing.

`frontend/src/themes/index.ts:263` still shallow-merges `chart`, so a future caller passing `{ chart: { series: { temp: "#..." } } }` through `createCustomTheme` would replace the whole `series` ramp with a partial object. This is not a current blocker because the existing ThemeEditor does not edit the new chart fields yet and `deserializeCustomTheme` handles legacy storage correctly, but the helper says "Deep-merge"; the nested `series` object should eventually follow the deserialize pattern.
