# Review: PR #340 Public Relay Sender + UI Audit

Date: 2026-08-14
Reviewed: PR #340 at `c807520ad2df1711c93a3c15fce3c5607fe76636`
Round: 1
Label applied: `changes-requested`

## What Is Correct

- Secret masking for both `public_mode_ingest_secret` and `public_relay_secret` is wired through `_SECRET_KEYS`, so `GET /api/config` does not return the bearer in clear text.
- The private-side relay re-reads `station_config` inside every `maybe_upload` call and gates on `station_driver_type == "public_relay"` before posting. A flip through `PUT /api/config` takes effect on the next broadcast for the sender path.
- The sender does not log the bearer header directly. Reading failures persist a synthesized status/detail string, not the outbound header, and the tests cover the normal wrong-secret detail.
- `public_mode_active` is computed server-side and mapped into `FeatureFlagsContext.publicModeActive`; the audited Settings surfaces read that flag consistently.
- The React hook-order changes are compliant. `DatabaseTab` and `BackupTab` call all hooks before their public-mode early returns, and `ChangePasswordCard` calls `useFeatureFlags` plus its local hooks before returning `null`.
- The wizard serializes `publicModeIngestSecret` as `public_mode_ingest_secret`, and `complete_setup` writes every `SetupConfig` field into `station_config`.

## Blockers

1. Public-droplet first-run setup leaves the wizard in an error state after committing public mode.

   `frontend/src/components/setup/SetupWizard.tsx:203` calls `completeSetup(config)` and only then calls `setupAdmin(...)` at `frontend/src/components/setup/SetupWizard.tsx:204`. For the new `public_relay` setup path, `complete_setup` writes `station_driver_type = "public_relay"` and `setup_complete = "true"` before committing at `backend/app/api/setup.py:150` and `backend/app/api/setup.py:173`, then invalidates the public-mode cache at `backend/app/api/setup.py:177`. From that point, the middleware at `backend/app/main.py:326` blocks every `POST` except the two ingest paths, so the following `/api/auth/setup-admin` request is rejected with 403.

   The result is that the droplet setup writes the ingest secret and marks setup complete, but the frontend catches the 403 and never calls `onComplete()`. On refresh, `/api/setup/status` reports setup complete even though no admin account was created. Public mode does not need an admin account, so the fix can be either to skip `setupAdmin` for `public_relay` or to create the admin before flipping into public mode, but this path needs to be made intentional and tested.

## What Needs Attention

1. Identity push failure bypasses the relay backoff.

   `_maybe_push_identity` retries on every broadcast when the config push fails because `_last_identity_hash` never advances (`backend/app/services/public_relay_sender.py:200` and `backend/app/services/public_relay_sender.py:208`). That retry path does not share `_push_reading`'s `_effective_interval` gate or `_apply_backoff` state (`backend/app/services/public_relay_sender.py:260`). A down droplet or wrong bearer therefore continues to receive `/api/ingest/config` attempts every poll cycle even after reading uploads have backed off. This is not a secret leak, but it weakens the intended self-limiting behavior and can spam the target during outages. Consider sharing the reading backoff gate for identity attempts or adding a small identity-specific retry timer.

## Bloat / Non-Functional

None. The sender is larger than a trivial uploader, but the additional state is tied to concrete requirements: config re-read, driver gate, persistent last error, backoff, and identity hash detection.

## Recommendations

- Add a regression test for public-relay setup order: submit `/api/setup/complete` with `station_driver_type = "public_relay"`, then assert the frontend path either does not call setup-admin or the backend supports the chosen order without a 403.
- Add a sender test showing failed identity pushes are rate-limited once the droplet is unavailable or credentials are wrong.
- Keep the `public_mode_ingest_secret` minimum in the wizard, but consider trimming whitespace before the length check to match the backend's ingest-secret read path.

## Bottom Line

Request changes. The private-side secret handling and driver gate look sound, and the frontend read-only hook/flag propagation is mostly correct. The public-droplet setup ordering bug blocks the advertised first-run wizard path for this final umbrella PR and needs a fix before landing.
