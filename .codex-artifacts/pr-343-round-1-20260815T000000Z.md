# Review: PR 343 public-mode read tightening

Date: 2026-08-15
Reviewed: PR 343 at 56afef5
Round: 1
Label applied: changes-requested

## What Is Correct

The Critical DB-dump path appears closed for configured public droplets. `GET /api/db-admin/export/backup` now depends on `require_admin_read`, and `require_admin_read` has no public-mode bypass. Because the bootstrap bypass is additionally guarded by `not is_public_mode()`, a public droplet with no admin users no longer falls through to the SQLite backup stream.

The same strict read dependency is also wired onto the high-risk read endpoints named in the sys_admin memo: DB stats, DB JSON export, backup list/download, logs, and API-key listing. `station_config` also remains non-exportable through the JSON table registry.

The bootstrap-state matrix is correct for the intended boundary: fresh and mid-setup private installs keep the no-user setup bypass; configured private installs require an authenticated admin; configured public droplets with no users do not get the no-user bypass. A first-run install before the operator has selected `public_relay` still behaves like the existing bootstrap-open setup surface, which is consistent with the current setup model and does not yet contain the configured public ingest secret.

## Blockers

1. `GET /api/config` still leaks the backup schedule time in public mode.

`backend/app/api/config.py:267` adds `_PUBLIC_MODE_HIDDEN_KEYS`, but the backup schedule entry is `"backup_schedule"` at `backend/app/api/config.py:279`. The actual config key is `"backup_schedule_time"` in `_DEFAULTS` and in the Settings UI (`frontend/src/pages/Settings.tsx:1282`). Since `get_config` only filters exact key names, public-mode guests still receive the saved backup schedule time. The config-surface memo called out the `backup_*` ops fields as the class to hide, and this PR already hides `backup_enabled`, `backup_interval_hours`, `backup_retention_count`, `backup_directory`, `backup_last_success`, and `backup_last_error`, so the missed key looks like a typo rather than an intentional exception.

Fix: replace `"backup_schedule"` with `"backup_schedule_time"` and add a seeded assertion for that exact key in `test_hidden_keys_absent_from_public_mode_response`, so this cannot regress behind the broad set-intersection test.

## What Needs Attention

The `_PUBLIC_MODE_HIDDEN_KEYS` comments say some hidden fields are not rendered by the read-only Settings UI, but several of them are rendered in the frontend when their tab is visible; the filter makes them blank rather than absent from the UI. That is acceptable from a security perspective for the third-party account IDs, but the comment and test wording should not claim the UI does not render them unless the frontend is also changed to hide those controls in public mode.

## Bloat / Non-Functional

None.

## Recommendations

Add a small regression test that seeds every hidden key with a non-default value and asserts all are absent from public-mode `GET /api/config`. The current set-intersection assertion catches typos only if the misspelled key is itself returned, which cannot happen for a non-existent config key like `backup_schedule`.

## Bottom Line

Request changes. The Critical SQLite dump leak is closed by the new dependency and route wiring, but the Medium config-surface remediation is incomplete because `backup_schedule_time` remains guest-readable in public mode.
