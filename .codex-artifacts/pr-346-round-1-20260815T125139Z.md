## What Is Correct

The `Persona` union and `isPersona` guard correctly protect both read paths that can carry untrusted strings. `getInitialPersona()` falls back to `DEFAULT_PERSONA` when localStorage contains an unknown value, and the mount-time backend reconciliation only updates state when `prefs.ui_persona` passes the same guard.

`PersonaProvider` is correctly placed inside `AuthProvider` and above the rendered app subtree. It is also inside `FeatureFlagsProvider`, matching the requested position for PR 4 shell consumers, and I do not see a provider-ordering hazard with `AlertProvider` or `DashboardLayoutProvider`.

The invisible-landing claim holds for rendering: the only `usePersona`/`PersonaProvider`/`ui_persona` references in `frontend/src` are the new context, `App.tsx` provider wiring, and preference defaults. No current screen or hook reads persona to change UI.

The public-droplet 403 path is handled by the current `writeUIPref` logic because `ApiError` messages for non-401 failures include `API <status>`.

Reviewer verification: `cd frontend && npx tsc --noEmit` passed.

## Blockers

1. `frontend/src/utils/uiPrefs.ts:86` only checks the rendered error message for `"401"`/`"403"`, but the API client throws `new ApiError(401, "Authentication required")` for 401s. That means the ordinary logged-out auth failure mode still falls through to `console.warn`, so the new contract does not actually swallow both anonymous cases. Check `err.status === 401 || err.status === 403` first, with the message-string fallback only as a secondary guard if desired.

## What Needs Attention

None beyond the blocker.

## Recommendations

After fixing the 401 status check, add a small unit-level check around `writeUIPref` if the frontend test setup has a convenient place for it; otherwise a targeted manual console smoke for logged-out non-public mode and public-droplet mode is enough for this narrow change.

## Bottom Line

Revise before merge. The persona narrowing, provider placement, and invisible landing are sound, but the requested 401/403 console-noise fix misses the 401 shape thrown by the local API client.
